# AI Provider 与 Nocterm Bridge 验收流程

## 目标

验证 Codex、Claude Code、Grok 从 AI 面板启动后，能够安全访问当前绑定的本地终端或 SSH 连接，并正确处理流式输出、会话上下文、只读策略、命令审批、停止、断线与资源清理。

本流程以实际行为和可留存证据为判据。浏览器预览、静态检查或 Provider 的自然语言回答不能替代 Tauri、真实 Provider 和真实 SSH 服务器之间的端到端验证。

## 安全边界

- 仅使用专用测试服务器和测试账号，不在生产主机执行审批测试。
- 通用命令只选择无副作用命令，例如 `pwd`、`id`、`echo NOCTERM_APPROVAL_OK` 和 `sleep 20`。
- 截图和日志不得包含密码、私钥内容、Token、完整环境变量或其他敏感信息。
- 权限按“仅分析 → 每次确认 → 变更前确认 → 完全访问”递增；完全访问仅限当前会话，仍受审计、目标绑定、限流、超时和取消约束。

## 前置条件

- 使用 Node.js 22、pnpm 11 和 stable Rust，并已完成 `corepack pnpm install`。
- 至少有一个本机 Provider CLI 已安装、已登录，并且从启动 Nocterm 的环境中可见。
- 准备一台非生产 SSH 测试服务器，建议同时准备第二台主机或第二个账号用于串线验证。
- SSH 测试账号可以执行 `uname`、`uptime`、`pwd`；Docker 用例还要求远端已安装 Docker，并允许测试账号执行 `docker ps`。
- 准备一个“不保存密码”的密码认证连接，用于证明 AI 复用已经认证的 SSH 会话。
- 测试 Codex、Claude Code、Grok 时分别记录 CLI 版本。当前版本不提供 GUI 路径或登录探测，若面板显示不可用，应先从同一启动环境确认命令是否在 `PATH` 中。

## 测试记录

每个平台和 Provider 分别保存一份记录：

| 字段         | 记录内容                             |
| ------------ | ------------------------------------ |
| 日期         | 实际执行日期和时区                   |
| Nocterm 版本 | 产品版本及待测 Git revision          |
| 工作区状态   | 是否包含未提交改动                   |
| 系统         | macOS/Windows 版本和 CPU 架构        |
| Provider     | 名称和 CLI 版本                      |
| SSH 服务端   | 系统、SSH 服务版本和脱敏连接名称     |
| 认证方式     | 密码未保存/密码已保存/私钥/SSH Agent |
| 用例结果     | Pass/Fail/Blocked，并附失败现象      |
| 证据         | 脱敏截图、控制台错误和必要日志位置   |

AI 输出具有非确定性，验收时检查目标、实际命令、返回值和生命周期，不要求回答文案逐字一致。主流程必须使用普通用户语言，不向用户暴露 MCP 或内部工具名。Provider 没有实际检查目标服务器时，可用相同提示重试一次；仍未执行则记录为 Fail 或 Provider 兼容性问题，不以自然语言猜测结果代替真实结果。

## 自动门禁

在仓库根目录执行：

```bash
corepack pnpm check
corepack pnpm cargo:check
git diff --check
git diff --cached --check
```

四条命令全部通过只是进入真实验收的前提，不代表 AI 功能已经验收。

Rust 自动测试还必须覆盖 SQLite v6 新建与 v5 升级、审计脱敏字段、30 天/10,000 条保留策略，以及审计前置写入失败时执行闭包没有被调用。真实验收记录不得直接附加数据库文件，因为其中仍包含本地连接主键和任务元数据。

## 最小验收路径

第一次测试可先完成以下闭环，预计 15 到 25 分钟：

1. 执行 AI-020，用“不保存密码”的连接证明复用当前 SSH 会话；
2. 执行 AI-022，验证 `docker ps` 和带格式参数的真实问题；
3. 执行 AI-023，证明只读入口不会接受命令拼接；
4. 执行 AI-024、AI-024A 和 AI-025，验证四级权限、允许/拒绝/单次授权和停止时撤销审批；
5. 执行 AI-030 和 AI-040，验证连续对话、主动停止及恢复。

任一项失败即停止标记“已验收”，记录现象后进入针对性修复。最小路径通过后，再完成目标隔离、断线、异常退出和其他 Provider 矩阵。

## 启动与基线

1. 从能够直接执行待测 Provider 的终端启动 `corepack pnpm tauri dev`。
2. 确认 Nocterm 显示 `desktop core ready`，AI 面板能打开，待测 Provider 显示可用。
3. 打开开发者控制台并清空旧错误；测试期间不应出现未捕获异常。
4. 记录启动前已有的 Provider 进程，避免把用户原有进程误判为 Nocterm 泄漏。

## 核心用例

### AI-001：无终端目标启动

1. 关闭所有终端标签。
2. 在 AI 面板发送：`你好，请简单介绍一下你能帮我做什么。`
3. 确认 AI 面板能够收到流式输出并正常结束。
4. 确认没有访问已经关闭的终端，也没有沿用上一次服务器的信息。

预期：Provider 可以作为无 Nocterm 目标的本机 Agent 启动；没有伪造或沿用上一次终端绑定。

### AI-010：绑定本地可见终端

1. 打开本地终端并等待 Shell 提示符。
2. 在 AI 面板发送：`帮我查看当前终端所在的目录。`
3. 观察本地终端和 AI 面板。

预期：

- 工具目标是当前本地终端；
- 命令回显和结果出现在可见终端，同时结果返回 AI；
- Provider 必须实际使用 Nocterm 当前终端能力，不得改用内置命令、GUI、REPL 或用户配置中的其他 MCP；
- 终端不显示 `printf` 状态探针、`__NOCTERM_LOCAL_AI_DONE_*__` 内部完成标记或其重绘片段；
- AI 工具结果包含当前 Shell 返回的数字退出码；
- 完成后终端仍可正常输入，AI 没有创建另一个不可见的本地 Shell。

### AI-010A：本地退出状态与并发隔离

1. 在本地终端请求执行一条会输出诊断文本并以 `7` 结束的命令：POSIX 使用 `sh -c 'echo NOCTERM_LOCAL_FAILED; exit 7'`，PowerShell/CMD 使用 `cmd /c "echo NOCTERM_LOCAL_FAILED & exit /b 7"`。
2. 批准后检查 AI 对失败的判断和终端中的实际输出。
3. 在同一本地终端同时从两个 AI 会话请求执行 `echo NOCTERM_LOCAL_SERIAL`，依次批准。

预期：第一条命令返回 `exitCode: 7`，AI 不得因存在输出而声称成功；内部随机标记及状态探针不显示在终端中。并发时只有一条命令进入 PTY，另一条明确提示当前已有 AI 命令，不能发生命令拼接、输出串流或过滤器覆盖；前一条结束后可重新请求。

### AI-020：复用已认证 SSH 会话

这是验证此前“AI 再次读取私钥或提示缺少凭据”问题的主用例。

1. 使用“不保存密码”的连接打开 SSH 标签，手动输入密码完成登录，并保持标签打开。
2. 在终端先执行 `uname -n`，记录脱敏后的主机标识。
3. 在 AI 面板发送：`帮我查看当前这台服务器的主机名。`
4. 观察终端标签、AI 工具过程和回答。

预期：

- AI 返回的主机名与当前标签手动执行的结果一致；
- 命令成功，且不再次索取密码、私钥或其他登录信息；
- AI 使用现有已认证连接上的独立 exec channel；
- `uname -n` 不写入用户可见 SSH PTY，当前 Shell 提示符和正在输入的内容不受影响。

判定：在未保存密码的前提下成功执行，是复用当前 SSH 会话的直接证据。如果返回“尚未提供登录密码”或“缺少 SSH 私钥”，本用例失败。

### AI-021：SSH 目标隔离

1. 同时连接两台主机，或同一主机的两个可区分账号；分别记录 `uname -n` 和 `id` 结果。
2. 激活目标 A 标签并执行 AI-020。
3. 等该轮结束后切换到目标 B 标签，重新发送相同请求。
4. 检查两次目标信息和命令结果。

预期：每轮只访问发送时绑定的连接；A、B 的 `connectionId` 和结果不混用，后台标签不出现命令或输出。切换目标后 Codex 应重建对应会话级 Bridge，不沿用旧目标 token。

### AI-022：Docker 只读诊断

在已连接 SSH 标签中依次发送：

```text
帮我查看当前服务器正在运行哪些 Docker 容器，并说明它们的名称、镜像、状态和端口。
```

```text
请把当前服务器正在运行的 Docker 容器按名称、镜像、状态和端口整理出来。
```

预期：AI 自动选择 Docker 结构化检查能力，用户不需要提供命令或格式参数；输出来自当前 SSH 目标；远端没有 Docker、服务未启动或权限不足时应返回带退出状态的真实错误，而不是声称已经列出容器。用户不需要知道 MCP 或工具名称。

### AI-023：任意 Shell 不进入自动执行

发送：

```text
帮我在服务器上执行下面这条命令：docker ps; echo NOCTERM_INJECTION_TEST
```

预期：命令包含拼接符号时不得命中智能自动执行策略，必须显示包含完整命令和正确目标的审批卡片；选择拒绝后 `NOCTERM_INJECTION_TEST` 不得执行。系统不能把失败包装成成功回答。

### AI-024：通用命令逐次审批

1. 在输入框将执行权限切换为“每次确认”。
2. 发送：`帮我在当前服务器上执行 id，查看当前用户身份。`
3. 核对审批卡片中的目标名称、用户名、主机、端口和完整命令，然后选择拒绝。
4. 再次发送相同请求，这次选择允许一次。
5. 第三次发送相同请求，不立即操作审批卡片。

预期：第一次命令不执行并返回用户拒绝；第二次仅执行一次并返回 `id`；第三次仍要求审批，证明允许没有升级为会话级授权。

再请求执行一条确定返回非零退出码并同时输出诊断文本的测试命令。AI 必须同时取得真实 `exitCode` 和输出并判断失败；不得把“通道正常关闭”误报为执行成功。SSH 服务端不返回 `exit-status` 时结果必须标为未知，不能猜测成功。

审计预期：拒绝路径形成 `requested/pending` 与 `rejected/denied` 事件；允许路径在实际执行前形成 `approved/pending`，完成后追加 `approved/succeeded` 或 `approved/failed`。事件不得包含完整命令及其输出。

### AI-024A：执行权限策略

1. 在输入框保持“变更前确认（推荐）”，发送“请读取当前工作目录”，确认 AI 调用 `pwd` 时不出现确认卡片且返回真实输出。
2. 发送“请执行 `uname -n`”或带参数的 `uname -n`，确认即使看起来是只读命令也会弹出确认（第一版仅自动放行无参数命令）。
3. 切换为“每次确认”，再次发送“请读取当前工作目录”，确认 `pwd` 也需要确认。
4. 在确认卡片中选择“允许一次”，再次发送同类请求，确认不会继承上一次授权。
5. 切换为“仅分析”，请求读取工作目录或查看服务器状态，确认不会执行终端工具，并返回明确的“仅分析”提示。
6. 在专用测试目标新建会话并选择“完全访问”，分别请求读取状态和执行 `echo NOCTERM_FULL_ACCESS`，确认均不弹审批；随后新建会话，确认权限恢复为“变更前确认”。

预期：策略只影响当前会话后续 turn；自动执行命令不发送审批 UI 事件但照常写入 `not_required` 审计；复杂参数、Shell 组合符号、未知或写入命令始终逐次确认。

### AI-025：审批等待期间停止

1. 发送：`帮我在当前服务器上执行 echo NOCTERM_APPROVAL_STOP。`
2. 审批卡片出现后，不批准，直接点击停止 AI。
3. 尝试操作旧审批卡片，然后发起一个新的只读请求。

预期：旧审批立即失效并按拒绝处理；`NOCTERM_APPROVAL_STOP` 不执行；旧审批不能在任务停止后恢复；新请求可以正常工作。

### AI-025A：迟到审批与会话隔离

1. 在会话 A 发起一条通用命令，等待审批卡片出现后立即停止任务。
2. 新建会话 B 并发起另一条通用命令，保留 B 的审批卡片。
3. 尝试点击 A 的旧卡片，再批准 B 的当前卡片。

预期：A 的旧卡片不可操作或返回已失效，且不能批准 B 的命令；只有 B 的当前审批能执行一次。界面快速双击“允许一次”也不得造成重复执行。

### AI-025B：审批超时与并行请求

1. 发起一条通用命令，保持确认卡片不操作并等待超过 60 秒。
2. 确认卡片已自动消失，再尝试通过 Provider 并行发起两条通用命令。
3. 在超时或并行请求被拒绝后继续发送一个结构化服务器信息查询。

预期：过期卡片不会永久残留，超时命令不会执行；同一任务最多展示一条确认，第二条并行请求明确失败且不能覆盖第一条；后续请求仍可正常完成，面板不无限加载。

### AI-026：常见运维问题

在当前 SSH 标签中分别发送：

```text
帮我看看当前服务器有哪些端口正在监听。
```

```text
帮我检查 Docker 服务现在是否正常运行。
```

```text
帮我查看 Docker 服务最近 50 行日志，重点找错误和警告。
```

```text
帮我查看容器 new-api 最近 100 行日志，并结合退出码、重启次数和健康状态分析为什么反复重启。
```

```text
帮我确认 Docker 当前是否配置了镜像加速器。
```

预期：AI 根据问题自动选择端口、服务状态、服务日志和 Docker 诊断的结构化能力；这些查询不弹出通用 Shell 审批，所有结果来自当前服务器，也不要求用户提供命令或了解内部工具。Docker 容器状态不得返回环境变量。没有 `ss`、systemd、Docker 或日志权限时，应返回真实退出错误，不能改到本机查询。

### AI-030：连续对话

1. 首轮执行 `uname -n`。
2. 继续追问：`刚才返回的主机名是什么？只回答该值，不要再次调用工具。`
3. 新建 AI 会话，再问：`刚才返回的主机名是什么？`

预期：同一会话第二轮能使用上下文；新会话不应知道旧结果。Codex 第二轮复用同一 app-server/thread；Claude Code 和 Grok 当前允许启动新进程，但必须通过 Nocterm 提供的对话上下文正确回答。

### AI-031：会话重置和目标变化

1. 在目标 A 完成一次请求。
2. 清空、删除会话或切换 Provider，再发送请求。
3. 从目标 A 切换到目标 B 后发送请求。

预期：旧 Codex thread 和 Bridge token 被回收；新请求不会收到旧会话输出；目标变化后工具只访问 B。旧会话迟到的 output/exit 事件不能覆盖当前会话状态。

### AI-040：主动停止与恢复

1. 发起一个需要较长推理但不执行写操作的请求。
2. Provider 输出期间点击停止。
3. 等待退出提示后立即发送一个简单的 `uname` 请求。

预期：停止后面板退出运行态，不再追加旧回答；Provider 与 Bridge 资源释放；下一轮可以正常启动。Codex 可使用协议中断，尚未取得 turn id 时允许关闭并重建 app-server。

### AI-040A：执行中停止

1. 通过通用命令请求在测试目标执行 `sleep 20`，批准一次。
2. 命令开始后点击停止，并观察审批、AI 状态和后续请求。
3. 立即发起一个简单的主机信息查询。

预期：执行在超时前被取消，旧任务不再返回成功或追加输出；后续请求取得新的 turn 授权并正常完成。

### AI-040B：折叠与恢复

1. 发起一个会产生多段流式输出或审批请求的任务。
2. 输出期间折叠 AI 面板，等待片刻后重新展开；再重复一次页面路由切换。
3. 若审批仍有效则操作当前卡片，随后检查停止按钮和最终状态。

预期：折叠和路由切换不会终止或重启 Provider，不丢失已有输出、当前审批和运行状态；重新展开后只存在一个事件流和一张审批卡片，不重复追加内容。

### AI-041：SSH 断线与目标关闭

1. 使用“不保存密码”的连接发起只读请求后，立即让测试 SSH 服务断线或关闭该连接的全部标签。
2. 观察 AI 面板的错误与退出状态。
3. 恢复 SSH 连接后重新发送请求。

预期：如果独立 exec channel 已经打开，本轮允许正常完成；如果尚未打开，应明确失败或取消。两种时序都不得无限加载、显示伪成功或串到其他连接，资源最终必须释放，恢复后新请求正常。当前产品只在发送时绑定状态为 `connected` 的活动标签，不要求在没有活动标签时自动选择连接。

### AI-042：UTF-8 与输出上限

1. 在测试服务器的测试服务中生成若干条长中文日志，使最近 500 行总量超过 128 KiB。
2. 请求查看该服务最近 500 行日志。
3. 检查回答末尾、终端状态和后续请求。

预期：命令在达到 128 KiB 上限后被中断并明确返回输出超限，不能用截断内容和未知退出码声称成功；已接收的 UTF-8 不出现 `�`，应用不崩溃，连接和 AI 面板仍可继续使用。

### AI-043：Provider 异常退出

1. 发起请求后，仅终止本轮由 Nocterm 启动的 Provider 子进程；操作前必须依据启动前基线确认 PID，不能终止用户原有 Provider 会话。
2. 观察 AI 面板并重新发起请求。

预期：面板显示真实退出状态或 stderr 摘要，不无限加载；Bridge token、审批和临时文件被清理；下一轮可以重新启动。

### AI-044：持续会话空闲后恢复

1. 使用 Codex 完成一次服务器信息查询，保持同一 AI 对话和终端目标不变。
2. 至少等待 90 秒，不折叠终端、不重连 SSH，也不发送新问题。
3. 在同一对话发送：`帮我查看容器 new-api 最近 100 行日志，分析它为什么反复重启。`
4. 批准本次通用命令，并继续发送一个结构化服务器信息查询。

预期：等待期间持续 Codex `app-server` 和 stdio Bridge 可以保持空闲；后续请求使用新的回环连接，不出现 `Transport closed`。批准后的命令只执行一次；即使响应阶段断线，也必须返回结果未知且禁止自动重试，之后的新请求仍可继续使用 Bridge。

## Provider 专项

### Codex

- 首轮冷启动后，连续追问不应再次经历完整 app-server 初始化。
- 停止 turn 后同一目标的后续请求可继续；目标变化或会话重置后必须新建 thread。
- Provider 自带 Shell 被禁用；目标绑定时 Nocterm MCP 必须成功初始化，否则 thread 启动失败，不能静默改用 GUI、REPL 或其他 MCP；Nocterm 只读工具不应被 Codex 自身审批再次拦截。

### Claude Code

- 输出以 `stream-json` 增量显示，最终完整消息不重复追加。
- 绑定 Nocterm 目标时不得使用 Claude 自带 `Bash` 绕过 Bridge。
- 单轮进程退出后不残留子进程或有效任务 token。

### Grok

- `streaming-json` 的 text、thought 和 error 事件分别进入回答、过程状态和错误提示。
- 绑定目标时不得使用自带 `run_terminal_cmd` 绕过 Bridge。
- 任务进程的 `GROK_HOME` 与 cwd 必须指向同一个任务级私有目录，`grok inspect --json` 不得显示启用的用户或项目 MCP、Hook 和兼容配置。
- 任务目录只允许链接既有 `auth.json`，不得复制认证内容；Prompt、Agent Profile、会话和日志全部位于该目录，正常退出、停止和启动失败后不得残留 `nocterm-grok-runtime-*`。

### Provider 输出边界

- 让测试 Provider 分别输出非法 UTF-8、超过 1 MiB 的单条 JSONL 和模拟读取失败；三种情况都必须显示明确错误并以失败结束，不能被当作正常 EOF。
- 失败后再次发送普通问题，事件监听和 Provider 进程管理仍可继续工作；Tauri 监听注册失败时面板不得启动一个无法接收结果的新任务。

## 结果判定

以下核心用例全部通过，才能把对应“平台 + Provider + SSH 认证方式”组合标记为已验收：

- AI-001、AI-020、AI-021、AI-022、AI-023；
- AI-024、AI-025、AI-025A、AI-025B、AI-026、AI-030、AI-031；
- AI-040、AI-040A、AI-040B、AI-041、AI-043、AI-044；
- 对应 Provider 专项检查。

AI-010 与 AI-010A 仅在验收本地终端目标时必测；AI-042 需要预置大日志，可单独记录为性能与边界验收。macOS 的通过结果不能代替 Windows，Codex 的通过结果也不能代替 Claude Code 或 Grok。

发现失败时记录最小复现步骤、Provider 原始事件类型、Nocterm 稳定错误信息和资源是否清理。不得把“重试后偶尔成功”直接记录为 Pass。

## 工程诊断附录

只有用例失败、需要定位集成层时，开发者才检查内部过程：远程目标应具备 `session_context`、十一个 `get_*`/`list_*`/`read_*` 结构化检查工具和受策略控制的 `ssh_exec`；本地目标只有 `session_context` 与受策略控制的 `local_terminal_exec`。旧 `ssh_exec_readonly` IPC 必须始终拒绝，且不得出现在 MCP 工具清单。这些名称不属于用户交互契约，不应出现在产品提示词、使用说明或要求用户输入的内容中。
