# AI 开发策略

本文件补充根 `AGENTS.md`，用于约束 AI 在 Nocterm 中的分析、修改、验证和交付行为。它不是代码风格清单，机器能够稳定检查的格式问题应交给 CI。

## 1. 事实优先

AI 在提出原因或方案前应收集与任务相称的证据：

1. 确认当前工作目录和工作区状态；
2. 阅读入口、调用方、实现、测试和关联文档；
3. 区分源码推断、自动测试结果和真实运行状态；
4. 对可能变化的依赖、平台和协议使用官方资料或本地实际版本；
5. 证据不足时明确边界，不用肯定语气补齐未知信息。

禁止仅因某个分支、提示文案或设计文档存在，就声称运行时一定走到了该路径。

## 2. 范围与变更策略

- 选择满足当前需求的最小完整变更，而不是最少行数的临时补丁；
- 发现邻近问题时先判断是否阻塞当前目标，不阻塞则记录并留在范围外；
- 不为未确认的 Linux、插件系统、多 Agent 或云同步提前设计实现；
- 功能开发前先明确行为契约、失败路径和回归用例；
- 重构必须有明确收益、受保护行为和验证方法，不与无关功能混合；
- 用户要求“讨论”或“评审”时不得自动实施修改。

## 3. AI 生成代码质量

AI 生成代码与人工代码使用相同标准：

- 不允许占位成功、硬编码演示结果或为了通过测试绕过真实行为；
- 不允许空 `catch`、忽略关键返回值、无说明的 `unwrap`/`expect` 或静默降级；
- 错误必须在所属边界转换，保留稳定错误码和可诊断原因；
- 状态任务必须拥有唯一 ID、显式状态、取消路径和唯一清理责任；
- 公共接口保持最小，抽象必须至少服务当前真实用例；
- 删除死代码优于保留注释掉的废弃实现；
- TODO 必须关联明确阻塞条件或跟踪项，不能代替当前需求。

## 4. 安全操作

以下操作必须在执行前说明具体目标、影响和恢复方式，并获得用户明确确认：

- 删除或覆盖文件、批量移动、数据库 Schema/数据变更；
- Git 提交、推送、重写历史、重置或切换工作分支；
- 新增/升级生产依赖、全局包操作和工具链升级；
- 调用生产环境、上传本地文件、发送日志或敏感数据；
- 修改系统权限、凭据、安全策略和环境配置。

授权只覆盖说明过的范围，不能推导为后续同类操作的永久授权。

## 5. 依赖与供应链

引入依赖前必须回答：

1. 标准库或现有依赖是否已经能解决；
2. 依赖是否仍在维护，许可证是否兼容 Apache-2.0；
3. 是否支持 macOS 和 Windows；
4. 是否进入最终安装包、接触密钥或执行外部代码；
5. 锁文件和 CI 是否覆盖该变更。

仅开发期且可移除的依赖也应保持最小；未使用依赖立即删除。

## 6. 验证证据等级

验证结果按以下等级描述，不得混用：

| 等级       | 可声称内容                                 |
| ---------- | ------------------------------------------ |
| 已检查     | 阅读了源码、配置、diff 或文档              |
| 已静态验证 | 格式、Lint、类型检查、Clippy 通过          |
| 已自动测试 | 明确列出的单元/集成测试通过                |
| 已构建     | Web、Rust 或 Tauri 构建命令成功            |
| 已运行     | 应用或服务启动并保持稳定                   |
| 已功能验收 | 在真实目标环境完成规定交互并观察到预期结果 |

例如，macOS 上 `cargo check` 不能证明 Windows 可运行；浏览器预览不能证明 Tauri IPC 已验收；Mock SSH 测试不能证明真实主机认证可用。

## 7. 变更类型与最低验证

| 变更                    | 最低要求                                              |
| ----------------------- | ----------------------------------------------------- |
| 文档                    | 格式检查、链接和命令人工核对                          |
| TypeScript 纯逻辑       | Lint、类型检查、相关 Vitest                           |
| React UI                | 前端门禁、真实浏览器/Tauri 视觉与交互检查             |
| Rust Domain/Application | rustfmt、Clippy、相关单元测试                         |
| IPC/DTO/Event           | 前后端契约测试、真实 Tauri 链路                       |
| SQLite Migration        | 新建库、逐版本升级、失败与回滚验证                    |
| 终端/SSH/SFTP/凭据      | 自动测试、真实 macOS/Windows 流程、安全与资源清理检查 |

如果环境无法满足最低验证，任务可以交付实现，但必须标记为“未完成验收”并列出用户可执行的准确步骤。

## 8. 最终交付

最终报告应简洁回答：

- 实现或发现了什么；
- 修改了哪些核心文件和边界；
- 运行了哪些检查及其结果；
- 哪些真实运行已经完成；
- 哪些内容未验证、为什么以及下一步是什么。

不得隐藏失败命令，不得以“理论上”“应该可以”替代验证结果。
